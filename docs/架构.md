# 一、项目目标

网站以内容发布为核心，支持文章、专栏、专题、普通介绍页和营销落地页。

基本要求：

- 使用 Astro 和 TypeScript。
- 首期支持简体中文和英文，语言路径分别为 `/zh/` 和 `/en/`。
- 内容来源为本地 SQLite 数据库。
- 执行 `pnpm run build`，从数据库读取已发布内容并生成可部署的网站文件。
- 文章正文、导航、页脚及主要 SEO 信息直接包含在生成的 HTML 中。
- 保留后续部署服务器、增加动态 API 和在线表单的能力。
- 内容页优先静态生成；需要运行时能力的功能独立设计。
- 数据库结构、公开 URL 和内部内容身份保持稳定，便于后续扩展。

一期重点完成内容展示、数据库发布模型、多语言、SEO、导航页脚和联系入口。后台管理界面、复杂权限及营销自动化作为后续扩展。

# 二、技术架构

请将项目划分为清晰的职责层：

1. 数据访问层：负责 SQLite 连接、查询、事务和迁移。
2. 内容服务层：负责已发布内容、语言版本、专栏成员和站点配置的读取。
3. 路由与 SEO 层：负责 URL、canonical、hreflang、sitemap 和重定向数据。
4. 页面与组件层：负责 Astro 页面、模板、导航、页脚和内容区块。
5. 可选运行时接口层：负责未来的联系表单等动态功能。

具体要求：

- 数据库访问仅在构建端或服务器端执行。
- 页面组件通过内容服务获取数据，避免到处散落 SQL。
- SQLite 文件保存在非公开目录，不进入 `public/`，不作为静态资源发布。
- 公共配置与服务器密钥分开管理。
- 预留存储实现边界，但一期只完成 SQLite，不同时实现多种数据库。
- 如果未来迁移 PostgreSQL，应提供明确的迁移路径，包括类型、约束、驱动和 SQL 差异。

Astro 网站使用静态输出。需要动态端点时，按实施时的官方配置方式接入 adapter，并仅让相应端点按请求运行。

## 2.1 前后端工作区边界（当前实现）

- 一个仓库通过 Bun Workspaces 管理 `apps/web`、`apps/admin`、`apps/api` 和服务端 Drizzle D1 包 `packages/db`；根脚本不合并应用职责。
- `apps/web` 使用 Astro 7 + Cloudflare Adapter。根语言入口可静态输出；双语首页、文章、专题、搜索、Sitemap 与 RSS 按请求读取 Workers 中 `CONTENT` 绑定的 D1。`bun run build:web` 不枚举 D1 内容，浏览器不直接查询数据库。SQLite SQL 仍是本地迁移源，旧 SQLite 文件不作为运行时回退。
- `apps/api` 使用 Elysia `1.4.32` 与 `CloudflareAdapter`，提供 `/health` 存活检查与单管理员认证 API。`apps/admin` 通过同源 `/api` 请求与 Eden Treaty 使用认证 API；前台 Astro 不依赖它。内容 CRUD 尚未实现。不以 `/health` 代替业务验证。

`bun run build` 聚合构建三个应用。API 的 Wrangler dry run 不执行上传或部署；远端配置未启用。验证命令与认证边界见 [README.md](../README.md#本地管理员)。

# 三、数据库与内容模型

如果附带以下 SQL，请先阅读并按顺序理解：

- `packages/db/migrations/astro_content_schema.sql`
- `packages/db/migrations/astro_site_schema_0002.sql`

保留现有模型的翻译、修订、发布、路由和站点配置能力。新增字段或表使用增量迁移。

核心模型如下：

| 表 | 主要职责 |
|---|---|
| `site_locales` | 语言配置，包括路径代码、语言标签和显示名称 |
| `content_items` | 稳定的内容身份，以及 article、page、collection 类型 |
| `content_translations` | 同一内容的不同语言版本 |
| `content_revisions` | 标题、正文、摘要、SEO 信息、模板和区块的修订快照 |
| `content_revision_seals` | 标记内容修订及其关联数据已封存 |
| `content_publications` | 每个语言版本当前公开的修订指针和发布时间 |
| `content_routes` | 当前规范路径、历史路径与目标内容的对应关系 |
| `collection_members` | 专栏或专题中的文章成员、顺序及展示属性 |
| `site_revisions` | 按语言管理的站点配置、导航页脚所属快照 |
| `site_publications` | 每种语言当前公开的站点配置版本 |
| `site_menu_items` | 顶部导航、页脚导航、法律链接和社交链接 |

## 3.1 内容身份与多语言

- 内容使用稳定 ID，不以 slug、标题或 URL 作为主键。
- 同一篇内容的中文和英文通过 `content_id` 关联。
- 每种语言可以拥有不同标题、正文、摘要、SEO 信息和 slug。
- 中文和英文可以独立编辑、独立发布。
- 没有发布的翻译，不生成公开详情页。

## 3.2 修订与发布

- 修订保存为不可变快照，编辑产生新修订。
- 公开查询只读取发布指针指定的修订。
- 保存草稿不会改变公开内容。
- 发布新版本通过切换发布指针完成。
- 新内容修订完成关联数据写入并封存后，才允许发布。
- 专栏成员、导航项等关联数据也需要随所属版本冻结。
- 封存保护覆盖新增、修改、删除及替换写入等操作。
- 区分首次发布时间、实际内容修改时间和构建时间。
- 每次构建不能自动刷新所有页面的内容修改时间。

需要明确：数据库中的发布状态改变后，静态网站仍需重新构建并部署，公开页面才会更新。

## 3.3 SQLite 约束

- 每个数据库连接启用外键检查。
- 为语言版本唯一性、路由唯一性和发布关系建立必要约束。
- 关键发布操作使用事务。
- 使用一致的 ID 和时间字段约定，沿用现有 SQL 的约定。
- 为公开内容、路由解析、导航和专栏查询建立必要索引。
- 提供版本化迁移和初始化示例数据。
- 构建使用一致的数据快照。
- 备份采用 SQLite 支持的一致性备份方式，覆盖 WAL 模式下的数据完整性要求。

# 四、文章、专栏与特殊页面

## 4.1 文章

支持标题、摘要、正文、封面、封面替代文本、SEO 信息、发布时间及修改时间。

Markdown 作为正文源格式。渲染 HTML 和搜索索引属于可重新生成的派生数据。

## 4.2 专栏与专题

- 专栏是具有独立介绍、SEO 信息和文章目录的内容页面。
- 专题可以复用 collection 模型，通过模板区分展示方式。
- 一篇文章可以属于多个专栏或专题。
- 专栏成员使用关系表管理，支持排序和推荐标记。
- 成员关系随专栏修订封存。
- 成员引用稳定文章 ID，展示该文章在相同语言下当前已发布的版本。
- 当前模型不要求专栏同时锁定所有成员文章的历史正文版本。
- 缺少对应语言的已发布文章时，按明确配置隐藏或使构建失败。

文章加入、退出或调整专栏，不改变文章自身 URL。

## 4.3 普通页面与落地页

普通介绍页、关于页、联系页和合作介绍页复用内容的翻译、修订、发布和路由能力。

使用有限的 `template_key` 和受控内容区块，例如：

- 介绍区；
- 图文区；
- 服务说明；
- FAQ；
- 联系 CTA；
- 文章或专栏列表。

区块应有类型、版本和数据校验规则，由代码中的组件映射负责渲染。

# 五、导航、页脚与站点配置

导航和页脚由数据库管理，并随站点配置版本发布。

支持以下位置：

- `header_primary`
- `footer_main`
- `footer_legal`
- `social`

要求：

- 中文和英文的文案、顺序及入口可以独立配置。
- 一期支持顶层链接、分组及分组下一级链接。
- 站内内容链接保存稳定内容 ID。
- 系统页面链接保存明确的 `system_key`。
- 外部链接保存经过校验的 URL。
- 构建时，将内部目标解析为对应语言的已发布 canonical URL。
- 修改内容路径后，导航链接能够跟随更新。
- 缺失目标按 `hide` 或 `error` 策略处理。
- 页脚支持版权信息、说明文字、联系入口和相关页面链接。

站点名称、默认 SEO 描述、Logo、默认分享图片及公开联系方式通过配置管理。机密配置留在服务器环境中。

# 六、URL 设计

## 6.1 默认路径

采用以下结构：

| 页面 | URL 示例 |
|---|---|
| 根语言选择页 | `/` |
| 中文首页 | `/zh/` |
| 英文首页 | `/en/` |
| 文章列表 | `/zh/articles/` |
| 文章详情 | `/zh/articles/astro-seo/` |
| 英文文章详情 | `/en/articles/astro-seo/` |
| 文章分页 | `/zh/articles/page/2/` |
| 专栏列表 | `/zh/columns/` |
| 专栏详情 | `/zh/columns/astro-guide/` |
| 可选专题详情 | `/zh/topics/technical-seo/` |
| 关于页 | `/zh/about/` |
| 联系页 | `/zh/contact/` |
| 可选合作介绍页 | `/zh/cooperate/` |
| 可选搜索页 | `/zh/search/?q=astro` |
| RSS | `/zh/rss.xml` |

英文路径遵循同样规则，但译文 slug 可以与中文版本不同。

## 6.2 路径规则

- HTML 内容页面统一使用尾斜杠。
- 示例规范地址为 `/zh/articles/astro-seo/`。
- 无尾斜杠版本重定向到规范版本。
- 默认使用小写 ASCII、数字和短横线组成 slug。
- slug 简短、可读，并在发布后保持稳定。
- 标题修改不自动修改 slug。
- 文章路径不包含可能变化的分类或专栏层级。
- 常青内容默认不在路径中加入发布日期。
- URL 不暴露数据库结构。
- 图片、脚本、`rss.xml`、`robots.txt` 等文件地址按文件路径处理。

当前 SQL 路径约束按 ASCII 路径实现。以后需要中文 slug 时，应同步调整数据库校验、编码和路径规范化规则。

Astro 配置采用与目录式输出配套的设置：

```ts
trailingSlash: 'always',
build: {
  format: 'directory',
},
```

请根据实际部署平台落实重定向。静态输出的部署方案，需要提供主机层面的跳转配置或等价实现，并说明验证方式。

## 6.3 路由数据与冲突

- 路由表存储语言与语言内路径。
- 生产域名由统一配置提供，不写死在内容记录中。
- 页面链接、canonical、hreflang 和 sitemap 使用统一 URL 生成函数。
- 当前路径与历史路径共用冲突检查范围。
- 系统路由、数据库内容路由和自动分页路由统一汇总检查。
- 发现重复或规范化后冲突的路径时，构建失败并报告具体记录。

注意：当前 `(locale, system_key)` 的规范路由唯一约束，不能直接表示多个分页实例。分页可由构建层生成，并参与完整路由清单的冲突检查。

## 6.4 URL 修改与删除

- 修改路径时保留旧路径记录。
- 历史路径指向稳定内容身份，并解析到当前规范地址。
- 部署环境使用真正的 HTTP 301 或 308 永久重定向。
- 历史地址直接跳到最终地址，避免多次跳转。
- 同步更新站内链接、canonical、hreflang 和 sitemap。
- 删除且没有合适替代内容时，返回真实的 404 或 410。

# 七、多语言与 SEO

## 7.1 语言关联

- 中文页面使用合适的 `lang`，当前按 `zh-Hans`。
- 英文页面使用 `en`。
- 中英文页面各自使用自己的 canonical。
- 通过相同 `content_id` 查找对应语言的已发布页面。
- 语言切换链接根据真实内容关联生成。
- slug 不同时，仍能正确找到译文。
- 没有译文时，隐藏该译文入口或明确说明，不生成虚假的页面地址。
- 不根据访问者 IP 强制跳转语言。

## 7.2 hreflang

- 仅声明实际存在、已发布且对应同一内容的语言页面。
- 使用绝对 URL。
- 包含当前页面自身和对应语言页面。
- 关联页面之间保持双向对应。
- `x-default` 只用于具有合适默认页面的场景。
- 根语言选择页可以作为首页语言组的默认入口。
- 文章的默认语言入口必须与该文章相关。

## 7.3 页面输出

根据页面类型输出：

- `<title>`
- description
- canonical
- hreflang
- Open Graph
- 社交分享信息
- 合适的结构化数据
- 面包屑及对应结构化数据

文章页使用适合的 Article 或 BlogPosting 结构化数据，字段与页面实际内容一致。

主要正文和可抓取的站内链接直接出现在 HTML 中，导航和分页使用真实的 `<a href>`。

## 7.4 Sitemap、RSS 与索引控制

- sitemap 只包含已发布、允许索引的规范页面。
- 排除草稿、历史别名、搜索结果和 `noindex` 页面。
- sitemap 的 `lastmod` 反映有意义的内容修改。
- RSS 只包含文章，不混入普通页面或专栏介绍页。
- 搜索结果默认 `noindex`。
- 筛选、排序及参数组合页面按需要控制索引。
- 需要搜索引擎读取 `noindex` 的页面保持可抓取。

分页拥有独立 URL 和自己的 canonical。第二页不能 canonical 到第一页。

营销参数不进入同内容页面的规范 URL。对会改变页面内容的参数，分别判断其处理方式。

## 8.1 表单扩展

如启用在线表单，可选择：

## 8.2 自建表单的数据

只有选择自建接收接口时，再实现运行时联系记录表。

建议字段包括：

- ID、创建时间和处理状态；
- 语言；
- 联系意图；
- 姓名；
- 联系方式类型和值；
- 描述；
- 来源内容 ID 和来源路径；
- CTA 标识；
- UTM 来源参数；

联系记录存入独立的运行时数据存储，例如 `runtime.sqlite`。内容构建和部署不得覆盖线上联系记录。

接口先持久化记录，再处理邮件等通知；通知失败应保留已接收的数据。

## 8.3 转化统计

区分以下行为：

- 点击联系按钮；
- 复制联系方式；
- 打开二维码；
- 表单被接收；
- 后续确认有效的联系记录。

保留外部营销来源参数。站内 CTA 使用单独标识，便于区分文章、专栏和页脚入口。
